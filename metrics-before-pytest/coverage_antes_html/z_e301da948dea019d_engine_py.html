1"""The engine on disk, once per process, and what to say while it is not. 

2 

3The browser is a patched Firefox of roughly a quarter of a gigabyte that the 

4core downloads from a GitHub release (`invisible_core.ensure_binary`) and 

5caches on this machine. Until 0.69.0 that download happened in one of two 

6places: inside `uvx invisible-playwright fetch`, run by a person who had read 

7the README, or inside the first browser launch, which from an MCP client 

8looked like a tool call sitting there for minutes and, on a client with a 

9short tool timeout, died with an error that named the timeout and never the 

10download. The README's fetch line existed for that reason alone. 

11 

12So the download is now a thing THIS PROCESS does, once, from the moment it 

13starts, and the two ways in use one object for it: 

14 

15* `invisible-playwright-mcp ui` runs it in the foreground, before the port opens, with a 

16 terminal line that follows it: the person launches the download and 

17 watches it, which is the way the owner asked for it to be on 2026-09-06 

18 when the first version of this (0.7.0 / server 0.13.0) was withdrawn. 

19* the MCP server runs it in a daemon thread from `main()`, because a client 

20 starts its servers at session start and the minutes before the first page 

21 are download time for free. `browser_open` does not launch a browser while 

22 the engine is not there: it answers with how far the download is and asks 

23 to be called again, so no tool call ever blocks on it and no client 

24 timeout is ever reached. Every other tool already answers "not open". 

25 

26⛔ A CALLER THAT BRINGS ITS OWN BINARY GETS NO DOWNLOAD. `--binary` on the 

27interface and `STEALTHFOX_BINARY` for the server (read by `plan.engine_here`, 

28the one reader of that variable) name an engine the person already has; the 

29launch still verifies it against the seal, as it always did. 

30 

31⛔ TWO DOWNLOADS IN ONE PROCESS RACE ON THE SAME TEMPORARY TREE: the core's 

32`ensure_binary` names it `.tmp-<tag>-<pid>` and removes it at the start of 

33every download, so a second caller deletes the first one's extraction. The 

34server never launches while this is in flight, and the interface runs it to 

35completion before spawning anything, so there is exactly one caller per 

36process and the race cannot start. Measured on the first version, 2026-09-05. 

37"""

49class Abandoned(BaseException): 

50 """Raised inside the download's progress callback when the process is 

51 leaving. A BaseException on purpose: the core's download loop wraps the 

52 callback in `except Exception: pass`, so an ordinary exception would be 

53 swallowed and the thread would go on downloading into a temporary 

54 directory nobody will ever clean. This one climbs out, the core's 

55 `TemporaryDirectory` unwinds, and nothing is left behind."""

58class Engine: 

59 """Where the engine is, for this process: not yet, coming, here, or given. 

60 

61 `state` is one of `pending` (nothing started), `downloading`, `verifying`, 

62 `extracting` (the core's three phases), `ready` (on disk, verified), 

63 `failed` (with `error`), `abandoned` (the process left mid-download) and 

64 `given` (a binary was named, nothing to download). `run()` does the work 

65 in the calling thread; `start()` does it in a daemon thread and is a no-op 

66 while one is in flight or once the engine is ready, so calling it from 

67 every `browser_open` costs nothing and is what retries a failed download. 

68 """
