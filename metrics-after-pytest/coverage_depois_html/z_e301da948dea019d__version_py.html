1"""What version the code being imported actually is. 

2 

3⛔ AN INSTALL RECORD IS NOT A DESCRIPTION OF THE CODE, AND FOR AN EDITABLE 

4INSTALL IT STOPS BEING ONE THE MOMENT SOMEBODY PULLS. `importlib.metadata` 

5answers about the DISTRIBUTION the installer put there. For a wheel that is the 

6same artifact as the code, so the number is right and there is nothing truer to 

7read. For `pip install -e` the metadata is written once and the code keeps 

8moving, and nothing says the two have parted. 

9 

10Measured on the machine this is developed on: the record said 0.54.0 while the 

11tree it points at said 0.68.8, fourteen patch releases apart, and the tree was 

12fully up to date at the time - pulling does not touch the record, which is what 

13makes this a defect in the code rather than a stale checkout. 

14 

15⛔ AND THE NUMBER WAS BEING ADVERTISED. `mcp/server.py` sets the `initialize` 

16handshake's `serverInfo.version` from it, under a comment saying the field 

17exists so a client can "correlate a defect with a release"; the interface puts 

18the same number in the `build` field it serves. That handshake had already been 

19wrong once, advertising the MCP SDK's version for every build of this package, 

20and the remedy replaced it with a number that is also not ours in the install 

21mode the maintainers use every day. 

22 

23⛔ A TEST HELD IT IN PLACE, AND THE WAY IT DID IS THE LESSON. It asserted that 

24the string `importlib.metadata` appeared in the source: a MECHANISM standing in 

25for the property that was actually wanted, which is `derived, never typed`. The 

26mechanism was the wrong one, so the test pinned the defect. This module answers 

27the property instead, and its test asserts the property. 

28 

29The version of the code is: 

30 

31 - a normal install: the install record, because the metadata and the code 

32 came out of the same build; 

33 - an editable install: the version the SOURCE TREE declares, because that is 

34 the code that will run, plus a `+editable` local segment (PEP 440) so it 

35 can never be read as the published release of the same number. An editable 

36 tree can carry uncommitted work, so a bare `0.68.8` would invite a bug 

37 report against a release that does not contain the code being run. 

38 

39Which of the two an install is comes from what the installer WROTE, not from a 

40guess about `__file__`: PEP 610 puts `direct_url.json` beside the metadata, 

41carrying `dir_info.editable` and the source directory. A wheel install has no 

42such file at all. 

43 

44The install record stays, under a name that cannot be mistaken for the version: 

45`pip`, `pip check` and anything reading `.dist-info` see that number, and 

46diagnosing the skew needs both. `invisible_core` made this same split first, 

47deriving its `__version__` from the seal it ships and naming the record 

48`__install_record_version__`; this is that decision, in the package that needed 

49it next. 

50 

51⛔ AND `invisible_playwright` CARRIES THIS SAME READING, DELIBERATELY NOT SHARED, 

52SO A CORRECTION HERE IS WORTH LOOKING AT THERE. Putting it in one place would 

53mean `invisible_core`, and this package does not depend on the core: it would 

54gain one for eighty lines of standard library, on top of a package the wrapper 

55already pins exactly, which is a second constraint on the same distribution from 

56two directions. Nor is there one mechanism to unify - the core derives from an 

57artifact it PACKAGES, which is a different reading for a different reason. No 

58FACT is duplicated here: each package answers about itself. The mechanism is, 

59and naming the twin is the whole of what stops that from rotting. 

60"""

108def declared_by(tree: Path) -> str | None: 

109 """The version that source tree declares, or None when it does not say one. 

110 

111 `pyproject.toml` is where the version lives and the metadata is a copy of it 

112 taken at build time, so this goes back to the source of the copy rather than 

113 adding a second source. A tree declaring `dynamic = ["version"]` says 

114 nothing readable without running its build backend, and answering None there 

115 falls back to the record, which is the same answer as before this module. 

116 """ 

117 try: 

118 parsed = tomllib.loads( 

119 (tree / "pyproject.toml").read_text(encoding="utf-8")) 

120 except (OSError, ValueError): 

121 return None 

122 declared = (parsed.get("project") or {}).get("version") 

123 return declared if isinstance(declared, str) and declared else None

126def versions(name: str = DISTRIBUTION) -> tuple[str, str]: 

127 """(the version of the CODE, the version in the install record). 

128 

129 The two differ exactly when the install is editable and the tree has moved 

130 since it was installed, which on a machine where this is developed is most 

131 of the time. `name` is a parameter so the behaviour can be tested against a 

132 real editable install of a real distribution rather than against a double. 

133 """ 

134 try: 

135 dist = distribution(name) 

136 except PackageNotFoundError: 

137 # A checkout on `sys.path` with nothing installed: no record to be 

138 # stale, and no recorded tree to read. 

139 return UNKNOWN, "" 

140 record = dist.version 

141 tree = source_tree(dist) 

142 if tree is None: 142 ↛ 143line 142 didn't jump to line 143 because the condition on line 142 was never true

143 return record, record 

144 declared = declared_by(tree) 

145 if declared is None: 145 ↛ 146line 145 didn't jump to line 146 because the condition on line 145 was never true

146 return record, record 

147 # Marked even when the two numbers agree: an editable tree is not the 

148 # published artifact whatever it declares, and that is what the marker says. 

149 return declared + EDITABLE, record
